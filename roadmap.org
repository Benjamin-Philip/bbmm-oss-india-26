*** Brief history of container runtimes
- Container technologies appeared after the invention of /cgroups/ and /namespaces/
- In 2013, Docker was created on top of [[https://linuxcontainers.org/lxc/introduction/][LXC]], introducing "packaging" of
  containers via images, and "portability" of images
- In 2014, ~libcontainer~ was released to create isolated processes and manage
  their life cycles
- In 2014, Kubernetes was announced
- OCI was created with ~runtime-spec~ and ~image-spec~
- ~libcontainer~ was donated to OCI to create ~runc~
- ~runc~ is a fully compatible API on top of ~libcontainer~ to spawn and manage
  containers
- Today, containers are split into 2 categories:
  - low-level: runc, gVisor, Firecracker
  - high-level: containerd, Docker, CRI-O, podman
- Runc is a standardised runtime, but it doesn't follow ~image-spec~
- High-level runtimes, like Docker and containerd implement this on top of runc
*** Runc
Any container consists of 2 parts:
- OCI configuration: JSON file with info on the container process
- Root filesystem directory: root filesystem used by container process via chroot

The OCI config has info on:
- [[https://man7.org/linux/man-pages/man7/capabilities.7.html][capabilities]]
- [[https://docs.huihoo.com/doxygen/linux/kernel/3.7/structtask__struct.html][task structure info]]
- [[https://www.linuxtopia.org/online_books/introduction_to_linux/linux_Mount_points.html][mount points]]
- [[https://man7.org/linux/man-pages/man7/namespaces.7.html][namespaces]]
- [[https://man7.org/linux/man-pages/man7/cgroups.7.html][cgroups]]

Key runc features include:
- Starting a container
- Pause and resuming a container
- Inspecting the state of a container
- Checkpoint (i.e. snapshot the current state) of a container with the help of
  [[https://criu.org/Main_Page][CRIU]], and restore a checkpoint (possibly on a different host)
- Execute a new process in an existing container
- Hooks

Rootless containers can be made, accounting the hierarchy of user namespaces.

*** DONE [[https://www.redhat.com/en/topics/containers/what-is-skopeo][What is Skopeo?]]
- Tool for manipulating, inspecting, signing, and transferring container images
- Docker CLI compatible
- Very useful for image distribution
- Notable commands:
  - ~skopeo inspect~: inspect image metadata without pulling the entire image
  - ~skopeo sync~: direct registry-to-registry, registry-to-files, and
    files-to-registry synchronisation
  - ~skopeo copy~: naive image copying
- Specialized tool, more flexible and agile to evolve than monolithic docker
- Benefits:
  - Rootless container management
  - Daemonless architecture
  - Native systemd integration
*** DONE [[https://www.redhat.com/en/topics/containers/what-is-buildah][What is Buildah?]]
- Builder for OCI images
- Allows you to:
  - Inspect, verify and modify images
  - Push images from local storage to a registry
  - Remove locally stored container images
  - Mount and unmount a working container's root file system
  - Use updated contents of an image as a layer for a new image
- Buildah and Podman are complementary
- Buildah is more fine-grained and allows lower level access than podman
- Buildah specializes in building container images
- Podman specializes in higher level tasks involved in creating, maintaining and
  running a container
*** DONE [[https://mkdev.me/posts/buildah-a-complete-overview][Buildah: A Complete Overview]]
- Rootless builder for OCI images
- Exposes a CLI interface for various Dockerfile/Containerfile directives
- Thus, instead of a Dockerfile, a shell script could build an OCI image
- Buildah's Rootless nature means that containers are scoped to a single system user
- Rootless containers are achieved by using Linux namespaces as much as
  possible, with cgroup v2 for resource management
- Application: OpenShift BuildConfigs - declarative and Kubernetes-native container builder
*** DONE [[https://docs.podman.io/en/latest/][What is Podman?]]
- Tool that handles everything to do with containers at a high level
- Can be used to:
  - Find containers on a container registry
  - Run a container
  - Build containers
  - Share or distribute containers
*** DONE [[https://last9.io/blog/podman-vs-docker/][Podman vs Docker]]
Major differences:
**** Daemon vs Daemonless
Docker uses a client-server model for containers, which allows centralized
management of containers.

Podman is daemonless and each container is completely independent from each other.
**** Root vs Rootless
Docker containers must run with root permissions due to the daemon. Podman
doesn't.
**** Tooling Compatibility
Podman aims to be as compatible with docker as possible, but incompatibilities
in Podman compose exist. Docker swarm is not supported.

*** DONE [[https://arxiv.org/html/2602.17678v1][It's Not Just Timestamps: A Study on Docker Reproducibility]]
Samples a stratified collection of GitHub repositories with Dockefiles.
**** Results
Reproducibility outcomes:
- as-is bitwise reproducibility is rare (2.7%)
- after infrastructure hardening, it becomes 18.6%
- most images do not become reproducible once infrastructure sources of non-determinism are removed
- developer-choices play a substantial role
Causes of non-reproducibility:
- Timestamps and metadata (100%)
- Formatting / file ordering (78%)
- System logs (43%)
- Caches and databases (36.8%)
- Compiled artifacts (20%)
- Application-specific files (13%)
- Random / non-deterministic data (9.4%)
- Package-manager state (5.6%)
**** Recommendations
- install system packages in a single ~RUN~ with ~--no-install-recommends~
- remove package index caches after every package installation
- pin base image and package installations to specific versions
- avoid baking runtime state or generated reports into the final image
